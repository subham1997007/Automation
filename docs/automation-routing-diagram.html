Overview

Jira Request Flow with MCP guardrails and grounded automation

Copilot or Windsurf never writes to Jira directly. Every request goes through jira-mcp, which gathers context, checks guardrails, and returns one controlled outcome: answer, proposal, approved update, or explicit block reason.

Jira action routing diagram

How Jira actions are routed

MCP routes each request to the right Jira path and enforces preview + approval before any write.

4

1. Classify the user request

Identify read-only, planning, create/update, or subtask intent.

Read-only route

Use jira_read_story and jira_analyze_story for no-write responses.

Planning route

Use jira_feature_context and jira_bootstrap_feature_stories for plan previews.

Create / update route

Use jira_refine_story and jira_create_story after approval gates.

Subtask route

Use jira_plan_subtasks and jira_manage_subtasks for controlled subtask actions.

3. Read-only requests return immediately

If no write is needed, return response directly.

4. Write requests enter preview gate

Show exact payload and wait for explicit approval.

5. Safety gate blocks incomplete writes

Block if required context, sprint, or approval is missing.

6. Return a controlled final result

Return success result, proposal, applied update, or stop reason.

Guardrails

Rules that keep the result controlled

These are the controls that keep Jira automation safe and predictable.

6
Gate 1

Read Current Jira

Before analysis or refinement, the current Jira story is loaded with fields, comments, links, and subtasks.

Gate 2

Feature Context Mandatory

If parent Feature or sibling stories cannot be loaded, Jira writing stops and the user must confirm the Feature.

Gate 3

Codebase Scan Mandatory

Story updates and creates must be grounded in actual repo context. No matching codebase evidence means no Jira write.

Gate 4

Proposal First

Refine, create, bootstrap, subtask apply, and delete flows show a preview before execution.

Gate 5

Explicit Approval

User must approve the exact proposed payload or action IDs. The tool blocks missing or mismatched approvals.

Gate 6

No Guessing

The tool does not guess sprint, parent Feature, or unrelated scope. Missing details return a question.

Gate 7

Evidence Returned

The result includes mode, planned changes, applied changes, block reason, or next action.

Rule

Jira Writes Stay Inside MCP

Copilot and Windsurf can suggest and explain, but Jira writes happen only through approved MCP tool calls.

GitLab action routing diagram

How GitLab actions are routed

MCP routes every GitLab request to the right path — branch ops, MR inspection, or controlled MR creation — after validating token health and branch state.

8

1. Classify the GitLab request

Identify branch management, MR inspection, MR creation, or token health check intent.

Branch management

Use gitlab_list_branches, gitlab_create_branch, and gitlab_git_status.

MR inspection

Use gitlab_list_merge_requests and gitlab_get_merge_request for read-only views.

MR creation

Use gitlab_prepare_merge_request then gitlab_safe_create_merge_request after checks.

Token health

Use gitlab_check_connection and gitlab_check_token_health before any API call.

3. Read-only & branch ops return immediately

Branch list, git status, and MR reads return results without further gating.

4. MR creation requires safety checks

Token health validated, branch pushed, title and description prepared before MR is opened.

5. Safety gate blocks on missing conditions

Block if token is expired, branch is not pushed, or source equals target branch.

6. Return a controlled GitLab result

Returns branch list, MR details, created MR URL, or a clear stop reason.

Databricks action routing diagram

How Databricks actions are routed

MCP routes each Databricks request — SQL queries, job runs, pipelines, dashboards, or vector search — through the correct compute path with resource validation.

9

1. Classify the Databricks request

Identify SQL query, job management, pipeline control, dashboard, vector search, or cluster operation.

SQL / Query

Use execute_sql with auto-selected warehouse for SELECT, DML, and DDL.

Jobs & runs

Use manage_jobs and manage_job_runs for scheduling and monitoring.

Pipelines

Use manage_pipeline and manage_pipeline_run for declarative pipeline control.

Dashboards & Vector Search

Use manage_dashboard and manage_vs_index for BI and semantic search.

3. Read queries and scans return immediately

SELECT queries, job status, pipeline state, and index scans are non-destructive and return fast.

4. Write operations require compute validation

Warehouse auto-selected or cluster ID confirmed before any job create, pipeline run, or DDL.

5. Safety gate blocks on missing resources

Block if no warehouse is available, cluster is terminated, or catalog/schema context is missing.

6. Return a controlled Databricks result

Returns query results, job run ID, pipeline state, dashboard URL, or a clear error reason.
